# Recovery inspection: display and touch

Inspected an attached timelm in ADB Recovery. ESP `/dev/block/by-name/esp`
resolves to `/dev/block/sda29`; Windows `win` resolves to `/dev/block/sda30`.
`esd` is not present. Both filesystems were mounted read-only for inspection.
Private registry hives, logs and device captures are stored outside this repo.

## Display

Recovery advertises `1080x2460x60x72564cmd` and a 30 Hz variant for the selected
SW43103 PV command-mode DSC panel. The local known-booting image SHA256 is
`464aaa27cd2d2af35f7857c89cc6081aa7787b0dc3beb5af62dfe6b4c8b75a78`.

The Windows SYSTEM hive was copied with LOG1/LOG2, replayed into a separate
local file, then inspected without loading or changing the live OS registry.
Its GraphicsDrivers configuration contains both:

- `PrimSurfSize.cx/cy = 1080/2460`
- `ActiveSize.cx/cy = 1080/2460`, rotation 1 (identity)

The firmware DSC already uses 1080x2460, and Windows uses the basic display
path. There is no evidence to justify changing framebuffer dimensions. The
reported visual sizing may be DPI/OOBE layout; runtime display/DPI information
is the next check. No DPI or resolution registry overrides were applied.

## Touch

Installed third-party hardware packages are GPIO, SPMI and PMIC; oem3 is the
Microsoft Print to PDF package. No touchscreen or Qualcomm GPU package is
present. Replayed Windows ACPI enumeration and the DSDT extracted from the
current boot image have no I2C controller or touchscreen device.

The phone's Linux SW42902 driver is bound to i2c-2/address 0x28 and reports
firmware v0.74 / B3W68TIM. Reset/IRQ are TLMM 38/39 and VCL/VDD enables 67/68.

A Windows source candidate is now under
`GPLDrivers/Windows/Sw42902Touch`. It corrects the G8 packet layout and
dimensions, replaces the G8 initialization sequence and hardens the SPB path.
Host packet tests passed, including ASan/UBSan. Full ARM64 KMDF compilation
also passed in [Actions run 39199989979](https://github.com/rofikkerneldev/test_mu-timelm/actions/runs/39199989979).
The package contains SYS/INF/CAT and a test certificate, with PE machine AA64.
Hardware validation remains pending; this is not a working touch release.

The next required integration is a verified Kona I2C SPB host and ACPI resource
contract. The three existing Kona drivers cannot provide I2C by themselves.
Keep the working DSDT and framebuffer while that dependency is resolved.

## Reproducible checkout

causing `prepare_timelm.py` to reject the unchanged checkout's SHA256 manifest.
The new `.gitattributes` disables text conversion for the byte-verified timelm
overlay. The local overlay was restored to its original LF bytes and verified
against the existing manifest; no firmware asset content was changed.

## Physical EFI clock capture and USB mass storage

The original clock-only once launcher ran on the phone, restored both Windows
EFI entry files to SHA256
`fae47d78487e781aa06466775cb461adeb7ff7f887fe2c15295bb2eb4f4954e1`,
and reached Windows Boot Manager. Original backups remain on ESP. The BCD has
subsequently changed during Windows boot; do not overwrite it with an older
capture merely because its hash differs.

EFI_CLOCK_PROTOCOL version 0x10009 reports:

| Clock | ID | Enabled | On | GetClockFreqHz |
| --- | --- | --- | --- | --- |
| gcc_qupv3_wrap1_s5_clk | 0x1010d | false | false | 0 |
| gcc_qupv3_wrap_1_m_ahb_clk | 0x100bc | true | true | 0 |
| gcc_qupv3_wrap_1_s_ahb_clk | 0x100d6 | false | false | 0 |

All three getters returned EFI_SUCCESS for these entries. The source-clock
name and alternate wrapper names returned an error, not a usable clock ID.
Frequency 0 is the protocol's reported value, including on the enabled master
AHB clock; it is not a measured source rate. The touch SE clock and slave AHB
clock are off at this snapshot. Keep the Windows I2C handoff gate disabled;
GENI firmware, pinmux, supplies and ownership still need validation.

UEFI USB mass storage exposes the 117.7 GiB LU0 disk to the PC. Its win volume
mounts as E: in this session; ESP is partition 29 and win is partition 30.
Drive letters and disk numbers must be rediscovered per session. ESP logs were
read through its exact volume GUID with an elevated, disk-validated helper;
no permanent drive letter or GPT attribute change was needed.

Current MassStorage.c assigns the raw LU0 BlockIO handle, so the host sees all
GPT partitions inside LU0. This does not mean every physical UFS LUN is exported.
Restricting export needs an explicitly bounded partition-backed implementation
and validation of the vendor USB MSD backend; hiding drive letters does not
remove raw access. The known-working mass storage firmware was not replaced.

The PC's DISM 10.0.26100.8972 /Image:E:\\ /Get-Drivers /All attempt failed with
error 87 and get_OSVersion HRESULT 0x80070057. Readable files do not establish
servicing compatibility. No driver servicing was attempted.

The captured Kernel-PnP Configuration log contains no USB controller/HID
enumeration. GPIO and SPMI started successfully, but PMIC (KONA1003/oem2.inf)
failed to start with problem 0xA and status 0xC0000185. This does not alone prove
the cause of USB failure. The current DSDT lacks a Windows USB host declaration,
while timelm's UEFI includes XhciPciEmulationDxe/XhciDxe/UsbConfigDxe/UsbInitDxe.
UEFI host role/PHY/VBUS and Windows ACPI/power integration need separate checks.
The next once-launcher build adds a getter-only USB protocol snapshot to the
same ESP log for a boot with OTG attached. No USB resources or role settings
have been guessed or enabled by this source change.

### USB snapshot on the physical V60

The USB-capable once launcher at 9d206cf ran with the user's OTG/keyboard test.
USB2_HC and USB_IO LocateHandleBuffer both returned EFI_NOT_FOUND (0x...000E),
count zero. Both Windows EFI entries were restored to the reference SHA256.
The new Windows Kernel-PnP capture still contains no USB device enumeration.
This establishes the absence of a published UEFI host at that instant; it does
not by itself prove a broken adapter, VBUS supply, CC detection or controller.

Source tracing shows PcdConInConnectOnDemand=TRUE and the Qualcomm input hook
signals gUsbControllerInitGuid. Static inspection of the captured LG UsbConfigDxe
matches that GUID to an event callback at RVA 0x1754; the callback invokes its
controller-start path with core 0/mode 4. That path's mode-4 branch installs and
connects the Peripheral Client Handle. Triggering this event is therefore not
evidence of a host-mode fix. No event or private protocol call was added.

The keyboard not moving the AOSP Recovery menu is only a user-visible symptom;
USB enumeration and input events must be checked independently. The user's
recollection that OTG used to work on Android is not a current hardware test.
Resources/Scripts/Collect-TimelmRecoveryUsb.sh records monotonic uptime, Type-C,
power-supply/extcon/USB role attributes, USB IDs, input devices and dmesg while
ADB is disconnected for the OTG test. It writes only a new /tmp folder, ignores
HUP so a cable swap can be captured, and never writes sysfs or partition data.
Start through Recovery ADB, wait for ready.txt, then swap the cable to OTG and
back. The default 90 samples have a 2-second delay plus attribute-reading time;
allow at least 3 minutes, longer on this Recovery.
complete.txt marks the end. Pull before reboot because /tmp is volatile.

### Recovery confirms OTG host and HID enumeration

The completed cable-swap capture contains 90 samples. On this Recovery plain
dmesg returned no output; the user's required `dmesg -S` returned the kernel
buffer and recovered the attach/detach sequence. The collector now uses -S.

At monotonic uptime 210.528 s the PM8150B charger enables OTG and usbpd starts
the primary USB host. xHCI buses appear at 210.588 s. At 210.973 s device
0461:0010 (NOVATEK USB Keyboard, bcdDevice 1.04) enumerates on USB 1-1. usbhid
and hid-generic bind and create keyboard, system-control and consumer-control
input devices. During attachment the sampled DWC3 mode is host, dual-role mode
is dfp/source, Type-C mode is Sink attached, CC orientation is 1, and voltage_now
is approximately 5.03 V. Here "Sink attached" describes the attached partner;
the phone's own power role is source. Do not treat usb/present=0 as absence of
an OTG partner: it remains 0 while these host and HID observations are present.

The disconnect at 235.668 s removes the keyboard, followed by the normal OTG
disable/xHCI teardown sequence. Reconnecting the PC restores ufp/sink/peripheral
and ADB. No forced role or voltage settings were used. Recovery kernel config
has USB_XHCI_HCD, USB_DWC3_DUAL_ROLE, USB_HID, HID_GENERIC and INPUT_EVDEV built in.

This proves successful CC/host/PHY/HID enumeration for this adapter and keyboard
in Recovery. The user reports no Caps/Num Lock response and no menu navigation;
the capture did not record raw EV_KEY events or LED output, so key delivery and
Recovery UI support remain unverified. The observed ID differs from the earlier
x86-reported 03F0:564A; do not assume it is the same peripheral identity.
The separate UEFI snapshot still has no USB2_HC/USB_IO handles, and the current
Windows DSDT lacks the USB host declaration. Recovery success does not supply
the missing UEFI/Windows initialization and ACPI/power integration.

### Recovery mouse input works

A second cable-swap capture using `dmesg -S` plus a bounded `getevent -lt`
listener confirms Logitech receiver 046D:C534 (bcdDevice 29.01). It enumerates
on the same primary host at uptime 457.142 s, publishes a mouse input device,
and binds hid-generic. The listener records REL_X/REL_Y events on the named
Logitech USB Receiver Mouse node; the user confirms cursor response in Recovery.
The captured input excerpt has no BTN_LEFT/BTN_RIGHT/REL_WHEEL events, so those
specific actions were not independently established by this test.

The collector now starts a getevent listener when getevent and timeout exist.
It monitors new input-device attachment and has an independent time bound;
ready.txt is written after launching it. No exclusive input grab, event injection
or role/power write is used. Mouse and keyboard captures have different USB IDs;
the earlier 03F0:564A reference is not used as a host-controller identity.

Recovery success rules out a universal inability of this phone/adapter to run
USB host with the tested peripherals. It does not establish host initialization
or firmware-to-Windows handoff in Mu. The UEFI host snapshot and missing Windows
USB ACPI resources remain separate unresolved integration problems.

### First native host probe and Windows repair follow-up

The physical 33a8a1a launcher restored both EFI entries, matched the LG USB
revision 0x10005 and LoadedImage method/code checks, but made no host request.
LocateProtocol returned the global dispatcher (core 2, mode 0x10000), which the
initial descriptor guard rejected. The override-variable queries all returned
EFI_NOT_FOUND; no persistent override value was established by that capture.

The Qualcomm UsbConfigInit reference explicitly installs a MAX_NUM/INVALID
dispatcher for starting controllers. The corrected guard accepts this exact

controller was removed. USB-HOST.md records the references and remaining gates.

The user reports Windows Automatic Repair after repeated interruptions during

The getter-only once variant retains its existing chainload behavior.

### V3 with OTG creates an operational UEFI host

The capture at 2026-10-19T09:05:46Z contains the completed cc6a440 run with OTG
attached. Before start, only the dispatcher existed. After start, core 0/mode 1
had PCI_IO and one QCOM BY_DRIVER open. One USB2_HC was operational, superspeed
capable, with two root ports and 64-bit addressing. Both port status/change
values were zero and USB_IO was absent after three seconds. This is a concrete
host transition, not successful mouse enumeration or proof of measured VBUS.

Cleanup restored mode 4, removed the PCI_IO/host protocols, and saved the shutdown
checkpoint; the user confirms automatic poweroff. Both Windows EFI entries and
immutable backups again match the reference. BCD remains 337a1ba8, identical to
the pre-test value. E: remains Healthy/NOT Dirty.

V4 retries standard recursive bus binding only on a sole, known-owner primary
USB2_HC handle with QCOM core 0/mode 1, PCI_IO, DevicePath and no existing host
protocol BY_DRIVER open. It records the binding result and a second USB snapshot
before normal teardown/shutdown. USB-HOST.md documents the precise gates and
the difference between QCOM emulation binding and USB bus binding. No general
ConnectAll, manual port-power operation or Windows USB activation was added.

The user's quoted Mu-Silicium maintainer advice correctly directs Windows
bring-up toward USB ACPI enumeration once a UEFI host is available. V3 supplies
that host-transition evidence; a UEFI mouse cursor is not a prerequisite for
